§1 Introduction; §2 Scaling Robot LearningRAX · Huang et al., 2026

00:20–01:05 · 45 seconds

Modern robot learning scales pretrained models and robot demonstrations. This gives broad semantic priors and useful action behavior. But this recipe primarily scales what happens before deployment. The paper asks what additional capability can come from the experience a robot collects after deployment.

Additional detail

The paper begins with the successful scaling recipe in modern robotics. Vision-language-action models adapt pretrained vision-language models to robot actions. World-action models bring video and dynamics modeling into this recipe. Both benefit from large amounts of robot demonstration data and substantial model capacity.

This is valuable progress: semantic priors from pretraining can be combined with embodiment-specific action experience. The question is what happens after this training stage, when we put the robot in a setting that the demonstration corpus does not adequately cover.

The authors motivate RAX as an additional scaling axis. They want to study experience acquired by the deployed agent itself. This framing is broader than simply replacing one policy architecture with another.

§1, paragraphs 1–2; §2 Scaling Robot LearningRAX · Huang et al., 2026

01:05–01:45 · 40 seconds

Two gaps remain: a new robot has different sensors and controls, and a new task introduces geometry or skill combinations not covered by demonstrations. The authors propose an explicit process for acquiring that missing task knowledge through interaction.

Additional detail

There are two deployment gaps in the introduction. The first is an embodiment gap. A new robot has different sensors, kinematics, grippers, and control interfaces. Even a generalist policy often needs demonstrations from that robot before it can be adapted.

The second is a task and environment gap. A robot may recognize the objects and know individual actions, yet still face a new arrangement or a new combination of skills. A static demonstration dataset does not explicitly provide an ongoing process for discovering a new strategy at deployment.

This is the authors' motivation, rather than a proof that every imitation-learning system cannot adapt. Their proposed answer is to let the robot collect and organize the experience it needs for the current task.

06:30–07:25 · 55 seconds

The backend provides calibrated sensing, low-level control, safety limits, and robot models or kinematic tools where available. The agent must discover the task-specific perception, grasps, control logic, and checks. This is the boundary behind the paper's claim about avoiding hand-engineered task primitives: it still uses substantial robotics infrastructure. On the real robots, general motion planning is not provided; long motions use short checked moves.

Additional detail

RAX is not starting from an unstructured hardware connection. The backend exposes calibrated sensing, state, low-level control, and safety limits. Depending on the platform, it also provides kinematics, inverse kinematics, motion planning, or a robot-only preview.

The frontend receives documents that explain the interface and the workflow. These are task-agnostic instructions, not a prewritten solution to the air fryer or another benchmark task.

The agent must develop the task-specific object model, perception pipeline, grasp strategy, control logic, and verification checks. The paper's phrase about avoiding hand-engineered action primitives refers to this task-solving layer. It does not remove the low-level controllers and robotics infrastructure.

This distinction also explains multi-embodiment support: the frontend organization stays similar while the backend and its interface documentation change.

Neither real robot provides a general motion planner. Long motions are composed from short checked moves. The humanoid tracker stabilizes reference poses, but walking is constructed by the agent from leg references and measurements. Compact tool responses retain full episodic recordings for later inspection.

Exploration discovers constraints that determine the motion. A front handle grasp leaves too little joint margin, so the agent grasps the upper arm of the handle from above. It pulls in three-centimeter increments. The eighteen-centimeter banana nearly fills the nineteen-centimeter basket, so the hand tilts by sixty degrees to create release clearance. Additional detail

This is the part of the method that a generic loop diagram misses. The agent discovers constraints that determine a successful solution.

For the handle, a human-like front grasp leaves insufficient joint margin near the arm base for the subsequent pull. The agent instead grasps the short horizontal arm on top of the handle. It then pulls in three-centimeter increments along the estimated drawer direction.

Placement is also constrained. The banana is eighteen centimeters long and the basket is nineteen centimeters wide. A level release brings the banana or opening fingers into contact with the fryer. The agent tilts the hand by sixty degrees and chooses a placement that clears the body.

These measured constraints become parameters and decision logic in the program. This illustrates the paper's claim that experience captures how to generate an action, rather than only storing the action that happened to succeed once.

Additional detail

RAX distinguishes working context, session notes, and a repository of verified skills. Session notes keep measured parameters and failure lessons available after the model's conversational context is compressed.

A skill repository adds a stronger contract. The skill includes code, conditions under which it applies, checks, and the evidence of a successful unattended execution. Later sessions can retrieve and compose these modules rather than rediscovering each behavior.

On the real robots, contributions are versioned and checked before being merged. This resembles software reuse with empirical execution evidence.

For interpreting the experiments, remember that simulation sessions begin with an empty task workspace. Their exploration curves mainly test learning within a session. The benefit of cross-task accumulated memory is illustrated separately in the real-robot continual-learning examples.

§10.1–10.2; §5.2.2

Development and submission detail

The paper provides a concrete workflow in Section nine. First, the agent reads the task and uses tools directly until it confirms a success. This establishes a working strategy before it tries to automate the whole task.

Next, it turns that strategy into observation-driven code. Each stage should check its preconditions, verify its result, and report states it was not designed for.

Then the program is used on further exploration episodes. New layouts force the program to measure geometry again. If a stage fails, the agent inspects the trace, intervenes, and edits that stage. This is the program-development loop that the previous high-level architecture figure summarizes.

Finally, benchmark submission freezes the program and requires an isolated rehearsal. This workflow is explicitly scaffolded by generic instructions. It is not an unspecified emergent behavior of an agent with no guidance.

Parallel agents can share the workspace and exploration ledger while trying complementary strategies. Parallelism changes elapsed collection time; it does not create an unlimited episode budget. The controlled configurations are in the supplementary parallel-exploration table.

§9 Agent Instructions and Skills; §10.2RAX · Huang et al., 2026

Appendix · outside the 30-minute main talk

This is optional detail for questions about program development and recovery. The main talk covers the development loop in the Method animation and submission conditions in Evaluation.

The paper provides a concrete workflow in Section nine. First, the agent reads the task and uses tools directly until it confirms a success. This establishes a working strategy before it tries to automate the whole task.

Next, it turns that strategy into observation-driven code. Each stage should check its preconditions, verify its result, and report states it was not designed for.

Then the program is used on further exploration episodes. New layouts force the program to measure geometry again. If a stage fails, the agent inspects the trace, intervenes, and edits that stage. This is the program-development loop that the previous high-level architecture figure summarizes.

Finally, benchmark submission freezes the program and requires an isolated rehearsal. This workflow is explicitly scaffolded by generic instructions. It is not an unspecified emergent behavior of an agent with no guidance.

Parallel agents can share the workspace and exploration ledger while trying complementary strategies. Parallelism changes elapsed collection time; it does not create an unlimited episode budget. The controlled configurations are in the supplementary parallel-exploration table.

Appendix · outside the 30-minute main talk

Here is the paper in one sentence: a coding agent develops and improves robot programs through online exploration, across different embodiments in simulation and on real robots. The architecture is shared, while each robot exposes its own sensing and control interface. The model weights stay fixed; programs, notes, and verified skills change. The main study asks whether more exploration produces better performance on unseen scenes. Let us first look at why this learning process is needed.

Additional detail

The distinction is between updating model parameters and updating an executable workspace. Exploration can add measured geometry, strategies, checks, and program revisions while the base model stays fixed.

The quantitative claim concerns performance on unseen scenes under each benchmark's evaluation contract. Simulation sessions start without prior task memory; cross-session skill reuse is evaluated separately on real robots.

The shared component is the agent architecture with platform-specific interfaces. The study does not claim that one program learned in simulation transfers unchanged across all embodiments. Real-robot sessions also acquire experience directly on the physical robot, with task-dependent operator support.
